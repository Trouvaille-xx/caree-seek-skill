# 反风控操作规范（Anti-bot protocol）

目标不是「绕过」平台风控，而是**用真实用户环境、以人类节奏**完成少量检索，避免触发不必要的风控与账号风险。
本工具的设计原则：**遇到风控信号立即停下，交给人处理**。

## 1. 环境选择（最重要）

| 方案 | 风控友好度 | 说明 |
|---|---|---|
| ego-browser / 用户真实 Chrome（有头、已登录） | 最高 | 真实指纹、真实 Cookie、用户可实时观察。**首选** |
| Playwright 有头 + 持久化 profile | 中 | 需配置 user-data-dir；否则每次新环境，风险高 |
| Playwright 无头 | 低 | 更容易被识别，且无法人工过验证 |
| 多标签并行 / 多实例并发 | 禁止 | 并发是最明显的机器特征 |

- 统一走单标签、单会话、串行操作。
- 不清理 Cookie、不频繁切换账号、不切换设备指纹。

## 2. 节奏参数（默认值，可按 `pacing_profile` 调整）

| 参数 | 保守 | 标准 | 激进（不建议） |
|---|---|---|---|
| 翻页间隔 | 15–25s | 6–10s | 3–5s |
| 详情页间隔 | 20–35s | 6–12s | 3–5s |
| 每批数量 | 10 | 15 | 20 |
| 批间休息 | 90–150s | 60–90s | 30–45s |
| 每关键词页数 | ≤2 | ≤3 | ≤5 |
| 单次总量上限 | 40 | 60–100 | 100（硬上限） |

建议：第一次跑用「保守」，确认稳定后再用「标准」。**永远不要用激进档做长时间抓取。**

## 3. 采集顺序的“人性化”

- 先搜索列表、再逐条看详情，符合真实用户行为。
- 不要用纯数字递增的 URL 暴力枚举全部页码；每关键词最多 2–3 页。
- 翻页优先通过页面自身的「下一页」点击（若可靠），其次才是改 URL 参数。
- 接口抽取（`extract-list-api.js`）本质是页面自身会发起的同源请求：一次页面加载 + 每页 1 次请求，保持与翻页一致的 6–10 秒节奏；`pageSize` 不超过 30；**绝不并发**。
- 每完成一个关键词可停顿更久（如 60–120s），模拟阅读与筛选。
- 一次 run 内不要频繁切换城市、关键词组合过多；控制在 1–3 个关键词、1–2 个城市。

## 4. 风控早期信号（出现任何一个就降速/停）

- 页面跳转到「安全验证 / 请完成验证 / 滑动验证」
- 出现「访问异常 / 操作频繁 / 环境异常」
- 搜索结果突然为空，但页面结构正常
- 再次要求登录（登录态被清）
- 详情页 403/空内容/重定向到首页

处理：
1. 立即停止动作，截图留档。
2. 按 playbook §6 交给人手动处理。
3. 恢复后降速到「保守」档，并把本次剩余预算减半。
4. 同一 run 连续 2 次风控信号 → 终止，建议 30–60 分钟或隔天再跑。

## 5. 数据量控制

- 单次 run 目标 60–100 条，硬上限 100。
- 每天建议不超过 1–2 次正式 run。
- 详情页尤其敏感：优先只对「高匹配候选」做详情，而不是全量打开。
- 断点续跑优先看已有数据是否够用，不要为了凑数反复重启。

## 6. 禁止清单

- 不允许自动过验证码、调用打码平台、注入 stealth/指纹伪造脚本。
- 不允许并发抓取、批量注册/切换小号、代理 IP 轮换规避。
- 不允许伪造请求头、绕过登录墙、抓取需要登录才可见的非公开数据。
- 不允许自动投递、自动打招呼、批量私信。
- 不允许采集 HR 个人隐私信息。

这些行为既超出工具设计边界，也会显著增加账号风险。

## 7. 记录与审计

每次 run 在 `state.json` 中记录：
- `captcha_events`：命中验证码次数
- `last_update`：最后动作时间
- `pages_done` / `jobs_collected` / `detail_done`

若连续多次 run 都有风控信号，应降低频率并在报告中提示数据可能不完整。
